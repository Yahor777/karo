# Recovery / No Wasted Limits

This document defines the Recovery contract for Karo Agent Core v1. Recovery is not a cosmetic state: it exists to preserve useful work, avoid repeating expensive stages, and make failures honest.

## Core Rules

- Timeout is not completed.
- Provider/model failure is not completed.
- Fallback is not success.
- Emergency fallback can only run after explicit user action.
- Partial staged artifacts must remain reviewable.
- Apply Changes is still required before any staged file reaches the project.
- Recovery UI must show real public activity, not hidden chain-of-thought.
- Raw diagnostics stay collapsed by default.

## Recovery State

Every recoverable failed run should expose:

- failedStage
- failedAgent
- failedFile when chunked generation fails on a file
- provider and model
- elapsedMs and timeoutMs
- selectedFiles and contextTokens
- partialArtifacts
- retryCount
- lastSuccessfulStage and lastSuccessfulArtifact when available
- recommendedAction
- fallbackUsed
- canRetryFailedStage
- canRetryReducedContext
- canContinueFromPartial
- canSwitchModel
- recoveryReasonUser
- recoveryReasonInternal

This state is surfaced to the UI through `TaskStateSnapshot.recoveryState`.

## Agent Website Recovery

Website generation is chunked by file. The current static website plan is:

- `src/karo-demo-site/index.html`
- `src/karo-demo-site/styles.css`
- `src/karo-demo-site/script.js`
- `src/karo-demo-site/README.md`

If a later file fails, earlier staged files stay in the artifact store. For example:

1. `index.html` succeeds.
2. `styles.css` succeeds.
3. `script.js` times out.
4. The run becomes `error` with `failedFile=src/karo-demo-site/script.js`.
5. `index.html` and `styles.css` remain staged.
6. Recovery can retry only `script.js` or continue from the first missing file.

Karo must not regenerate a fallback scaffold automatically and must not claim the benchmark passed until model/agent-generated staged files satisfy deterministic validation.

## Recovery Actions

### Retry Failed Stage

Retries the failed stage/file when a saved runtime exists.

For website generation, this retries only the failed chunk. It does not restart Researcher or recreate already staged files.

For read-only Chat/Plan/Security failures, it reruns the same read-only route from saved input. It does not switch into Agent Mode and does not create artifacts.

### Retry With Reduced Context

Retries with a smaller prompt/context budget.

For website generation, the retry omits the Researcher summary and sends only the original prompt, file plan, current target file, and constraints.

For read-only project-context tasks, the next Context Engine call halves the max file count and max total characters. This reduces token pressure while preserving the same mode and safety rules.

### Continue From Partial Artifacts

Continues from the first missing or failed file when chunked generation runtime is available.

Existing staged artifacts are preserved and are not deleted. Karo should continue with the next missing chunk, then run deterministic validation again.

### Switch Model

Inline switch is not fully wired in this pass. The UI may direct the user to the Models screen, but it must not present Switch Model as a primary ready action unless the action is actually connected.

### Emergency Fallback

Emergency static scaffold is a manual recovery option only. It must be clearly labeled as emergency fallback. It cannot pass the one-prompt website benchmark and cannot be reported as normal model-generated success.

## Plan and Chat Failures

Plan and Chat are read-only.

If the model/provider times out:

- no artifacts are created;
- no Apply Changes appears;
- status is error/recovery, not completed;
- current selected context summary is preserved for retry when available;
- retry keeps the same mode.

Plan Mode must not show a fake plan when the provider is unavailable or output cannot be parsed.

Chat Mode must not silently route a retry into Agent Mode.

## UI Wording Rules

Recovery cards should show:

- failed stage/agent/file;
- provider/model;
- elapsed/timeout;
- what was preserved;
- partial artifacts;
- recommended next action;
- enabled actions only when wired;
- disabled actions with a clear reason.

The UI must not say:

- Completed
- Ready
- Verified
- Applied
- Generated by model

unless that is true for the current run state.

## Benchmark Pass/Fail

The one-prompt website benchmark passes only when:

- Agent route was selected;
- staged website files exist;
- Apply Changes is required;
- deterministic validation passes;
- Preview/Open flow is available after Apply;
- fallback was not used as success.

The benchmark fails when:

- output is fallback-only;
- the run is in recovery/error;
- provider timeout left zero useful staged artifacts;
- required sections are missing after validation;
- Karo claims success without staged reviewable files.

## Current Implementation Notes

Recovery state and actions are implemented in:

- `apps/desktop-windows/src/orchestration/types.ts`
- `apps/desktop-windows/src/orchestration/desktopOrchestratorTransport.ts`
- `apps/desktop-windows/src/ui/workbench.ts`

Tests cover:

- Coder provider timeout creates recovery state.
- Website partial artifacts are preserved.
- Continue from partial artifacts resumes missing files.
- Reduced-context retry lowers read-only Context Engine budget.
- Chat/Plan provider timeout remains read-only and creates no artifacts.
- UI exposes recovery actions without fake success.
